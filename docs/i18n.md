# Internationalisation

MetaForger 1.0 ships in English only, but the structure for more languages is in place: adding a language is a translation task, not a refactor. This page explains how the pieces fit together. A complete "Adding a language" guide will follow with the 1.0 documentation set.

## How it works

| Piece | Where | What it does |
|-------|-------|--------------|
| Language files | `lang/<code>/*.php` | Standard Laravel translation files, one per area (`auth.php`, `ui.php`, ...). |
| Supported languages | `config/i18n.php` (`APP_SUPPORTED_LOCALES`) | Allow-list of two-letter codes. Default `en`. |
| Locale selection | `App\Http\Middleware\SetLocale` | Picks the language per request: signed-in user's `locale` preference, then the `locale` cookie, then the browser's `Accept-Language`, then `APP_LOCALE`. Anything not in the allow-list is ignored. |
| Front-end strings | `config/i18n.php` (`shared_groups`) | Groups sent to the browser with every page as a shared Inertia prop (`translations`). Default: `ui`, `members`, `legal`. |
| Strings for some pages only | `translations` route middleware (`App\Http\Middleware\ShareTranslationGroups`) | `->middleware('translations:auth')` adds a group to what the pages of that route receive. The sign-in pages use it: the `auth` group is 66 strings, 3.8 kB (1.2 kB compressed), which on every page would be 48 % more translations than the pages carry now. |
| Composable | `resources/js/composables/useI18n.ts` | `t(key, replacements)` and `tc(key, count, replacements)`. Works during server-side rendering. |
| Message syntax | `resources/js/lib/i18n.ts` | Mirrors Laravel: `:name`, `:Name`, `:NAME` placeholders and `one|many` / `{0} none|[2,*] many` plural forms. |
| Completeness check | `php artisan lang:check` | Fails if a language is missing keys the fallback language has. Runs in CI. |
| Key check | `tests/Feature/TranslationKeysTest.php` | Fails if the front end uses a key that is not in `lang/en`, reads a group that no page is sent, or an auth page is not sent a key it (or its layout) shows. A key that is missing shows as its own name, which nothing else would notice. |
| Literal-text check | `eslint.config.js` (`vue/no-bare-strings-in-template`) | Warns about English written in the template of a converted file. The rule is on for the files already converted (listed in the config) and a file is added when it is converted; a warning, not an error. |

A user's `locale` column (for example `fr_CA`) is a formatting preference that accepts any ICU locale. For the interface language only its language part (`fr`) is used, and only if it is in the allow-list.

## Using translations in Vue

```vue
<script setup lang="ts">
import { useI18n } from '@/composables/useI18n';

const { t, tc } = useI18n();
</script>

<template>
    <h1>{{ t('ui.nav.home') }}</h1>
    <p>{{ t('ui.footer.rights', { year: 2026, name: 'Acme' }) }}</p>
    <p>{{ tc('shop.items', cart.count) }}</p> <!-- "one item|:count items" -->
</template>
```

A missing key renders as the key itself and logs a warning in development, so gaps are easy to spot.

## Adding strings

1. Add the key to `lang/en/<group>.php`.
2. Make sure the browser is sent the group. If every page needs it, list it in `config/i18n.php` `shared_groups`, and keep that list short: everything in it is sent with each page. If only some pages do, put `translations:<group>` on their routes, as `routes/auth.php` does.
3. Use `t('group.key')` in the component.
4. Run `php artisan lang:check`.

## Adding a language (outline)

1. Copy `lang/en` to `lang/<code>` and translate the values.
2. Add the code to `APP_SUPPORTED_LOCALES` (for example `en,fr`).
3. Run `php artisan lang:check` until it passes.
4. Let users choose it: the profile `locale` setting already feeds the middleware, and the `locale` cookie covers visitors who are not signed in.

## What is translated today

Converted to keys in this release: the header navigation and buttons, the skip link, the footer and the theme menu, and the seven sign-in and password pages (log in, register, forgot password, reset password, confirm password, verify email, two-factor challenge) with their layout (`lang/en/auth.php`). The server's own messages on those pages, such as the answer to a wrong password, were keys already.

Still literal English: the menus in `AppHeader.vue` and `UserMenuContent.vue`, the settings navigation, the notification emails and the rest of the interface. Converting them is tracked in [docs/ROADMAP-v1.0.0.md](ROADMAP-v1.0.0.md) (section 8B): new screens written for 1.0 use keys from the start, and bulk extraction of the older pages follows in 1.1.

Conventions for new code: use keys, never concatenate translated fragments (a sentence that ends in a link is one string for the link, as "Back to log in" is, not a sentence and a link side by side), and prefer logical CSS utilities (`ms-`, `me-`, `ps-`, `pe-`) so right-to-left layouts stay possible. A key cannot have the same name as a string beside it: `auth.password` is a message, so the word "Password" is `auth.common.password`.
