# Internationalisation

MetaForger 1.0 ships in English only, but the structure for more languages is in place: adding a language is a translation task, not a refactor. This page explains how the pieces fit together. The steps to add a language, and what a new language does not reach, are in [adding-a-language.md](adding-a-language.md).

## How it works

| Piece | Where | What it does |
|-------|-------|--------------|
| Language files | `lang/<code>/*.php` | Standard Laravel translation files, one per area (`auth.php`, `ui.php`, ...). |
| Supported languages | `config/i18n.php` (`APP_SUPPORTED_LOCALES`) | Allow-list of two-letter codes. Default `en`. |
| The site's own language | `config/i18n.php` (`default`, from `APP_LOCALE`), `Locales::default()` | What is used when nothing asks for another language. Ask for it here and never from `config('app.locale')`: Laravel's `setLocale()` overwrites that with the language of the request in hand (and while an email is made in someone's language), so it is the language in use, not the site's. |
| Locale selection | `App\Http\Middleware\SetLocale` | Picks the language per request: signed-in user's `locale` preference, then the `locale` cookie, then the browser's `Accept-Language`, then `APP_LOCALE`. Anything not in the allow-list is ignored. Nothing in the site writes the `locale` cookie yet, so a visitor who is not signed in is given the language of their browser ([who sees which language](adding-a-language.md#who-sees-which-language)). |
| Front-end strings | `config/i18n.php` (`shared_groups`) | Groups sent to the browser with every page as a shared Inertia prop (`translations`). Default: `ui`, `members`, `legal`. |
| Strings for some pages only | `translations` route middleware (`App\Http\Middleware\ShareTranslationGroups`) | `->middleware('translations:auth')` adds a group to what the pages of that route receive. The sign-in pages use it: the `auth` group is 66 strings, 3.8 kB (1.2 kB compressed), which on every page would be 48 % more translations than the pages carry now. The settings pages use it for the words of their frame (`settings`, 18 strings, 740 B, 289 B compressed), which no other page is sent. |
| Messages the server writes | `lang/en/forms.php`, `validation.php`, `passwords.php` | What a member is told when a form or an action is refused. Written by the server in the language of the request, so these groups are never sent to the browser. See [Form messages](#form-messages). |
| Language of a recipient | `User::preferredLocale()` (`HasLocalePreference`), `AppSupportLocalizationLocales` | What is sent to a person, an email or a notice in the site, is in their language, not the language of the request that caused it. See [Emails](#emails). |
| Composable | `resources/js/composables/useI18n.ts` | `t(key, replacements)` and `tc(key, count, replacements)`. Works during server-side rendering. |
| Message syntax | `resources/js/lib/i18n.ts` | Mirrors Laravel: `:name`, `:Name`, `:NAME` placeholders and `one|many` / `{0} none|[2,*] many` plural forms. |
| Completeness check | `php artisan lang:check` | Fails if a language is missing keys the fallback language has. Runs in CI. |
| Key check | `tests/Feature/TranslationKeysTest.php` | Fails if the front end uses a key that is not in `lang/en`, reads a group that no page is sent, or an auth or settings page is not sent a key it (or its layout) shows. A key that is missing shows as its own name, which nothing else would notice. |
| Server key check | `tests/Feature/ServerTranslationKeysTest.php` | Reads the PHP and the Blade views of the app, and fails if a call names a key of a `lang/en` group (`mail.`, `forms.`, `auth.`, `errors.`...) that is not in `lang/en`, or gives a sentence other values than it asks for (`:name` asked for, `:title` given). Also fails if the copies of the framework's `validation.php` and `passwords.php` lack a key the framework has ([Form messages](#form-messages)). |
| Mail language check | `tests/Feature/Mail/MailLanguageTest.php` | Fails if an email, a notice or a digest line is written in the language of the request and not the recipient's ([Emails](#emails)). |
| Literal-text check | `eslint.config.js` (`vue/no-bare-strings-in-template`) | Warns about English written in the template of a converted file. The rule is on for the files already converted (listed in the config) and a file is added when it is converted; a warning, not an error. |

A user's `locale` column (for example `fr_CA`) is a formatting preference that accepts any ICU locale. For the interface language only its language part (`fr`) is used, and only if it is in the allow-list.

## Using translations in Vue

```vue
<script setup lang="ts">
import { useI18n } from '@/composables/useI18n';

const { t, tc } = useI18n();
</script>

<template>
    <h1>{{ t('ui.nav.home') }}</h1>
    <p>{{ t('ui.footer.rights', { year: 2026, name: 'Acme' }) }}</p>
    <p>{{ tc('shop.items', cart.count) }}</p> <!-- "one item|:count items" -->
</template>
```

A missing key renders as the key itself and logs a warning in development, so gaps are easy to spot.

## Adding strings

1. Add the key to `lang/en/<group>.php`.
2. Make sure the browser is sent the group. If every page needs it, list it in `config/i18n.php` `shared_groups`, and keep that list short: everything in it is sent with each page. If only some pages do, put `translations:<group>` on their routes, as `routes/auth.php` does.
3. Use `t('group.key')` in the component.
4. Run `php artisan lang:check`.

A message that the server writes (a form that was refused, an action that was not allowed) is a key of `lang/en/forms.php` and is written with `__('forms.group.key', [...])`. Nothing has to be sent to the browser for it. `ServerTranslationKeysTest` fails for a key that is not in the file.

## Form messages

What a member is told when something they did is refused is written by the server, in the language of the request (`SetLocale`), and arrives with the answer, so none of it is in the groups sent to the browser. It comes from three files:

- `lang/en/validation.php` and `lang/en/passwords.php` are copies of Laravel's own English files, with `custom` empty. They are copies on purpose: Laravel reads its own `lang/en` underneath the app's, so a key that is missing from the app's copy still shows in English, and `lang:check` would never ask a language to translate it. `ServerTranslationKeysTest` fails when the framework has a key the copy has not, which is what an upgrade that adds a rule looks like: copy the key in. The names of fields in these messages (`:attribute`) come from `validation.attributes`, which is empty, so a message says "nickname" as the form calls it.
- `lang/en/forms.php` is everything Laravel's rules cannot say: an API key that is refused, a promotion code that is not valid, a post that looks like spam, a message to someone who is ignored, a picture that is too large (71 sentences). Each is a whole sentence with its `:placeholders`, and anything that counts is a `one|many` pair read with `trans_choice` (`forms.api_keys.too_many`, `forms.forum.attachments_max`), so "1 file" and "2 files" are both right.
- The validator fills in `:attribute`, `:min`, `:max` and the like for a message of its own, so a form's `messages()` does not give them, and the check above knows which they are.

## Emails

The 21 notifications the site sends (account, moderation, orders, subscriptions, support, community, the data export, the daily digest) read their words from `lang/en/mail.php`. The notice in the site (the bell) and the browser alert are made from the same keys, so a sentence is translated once.

**Whose language.** The language of the person the email is for, chosen when it is sent, not the language of the request that caused it: a moderator working in English who lifts a ban writes to a member who reads French in French. `User` implements Laravel's `HasLocalePreference`, and `preferredLocale()` is the `locale` setting's language if the site has it and the site's own language (`Locales::default()`) if not, never the language of the request: a member whose stored language the site does not offer is written to in the site's, whoever caused the email. Laravel asks for it for every channel (mail, database and broadcast) and, for a queued notification, when the job runs, so a member who changes language while an email waits gets it in the new one. The notice stored in the site stays in the language it was sent in; it is not translated again when it is read.

**Three places where a notification would otherwise be in the wrong language**, and what handles them:

- *The daily digest keeps one line for each update until the morning.* The line is made when the update happens, while the request may be in another language, so `EmailDigest::hold()` makes it in the recipient's language (`Locales::within()`).
- *The emails about an order go to the address given at checkout*, which is not a user and has no language of its own. The listeners (`SendOrderConfirmation`, `SendOrderShippedNotification`, `SendRefundNotification`) pass `Order::notificationLocale()`: the buyer's own language when the order belongs to an account, else the site's. An order does not store the language the buyer browsed in, so a guest is written to in the site's language. Storing it is a column and a checkout change, and not part of 1.0.
- *A notification is sent outside a request* (a command, the scheduler, a queue worker): the application is in the site's language there, and the recipient's is used all the same.

**Writing a notification.** Use `__('mail.group.key', [...])`, one whole sentence for each key with its `:placeholders`, and `trans_choice` for anything that counts (`mail.digest.intro`). Never join translated pieces; a name, a number or a date comes in as a placeholder, because another language puts it in another place. The greeting is `MailText::greeting($notifiable)`. Text a person typed still goes through `MailText::quoted()` or `ApiKeyCreated::literal()`, as in [email.md](email.md#writing-a-notification). `MailLanguageTest` fails for a key that is not in the file and for a value that is not given (or given and not used).

**What is not in `lang/en/mail.php`:**

- *The words Laravel itself puts in an email.* The framework's "Verify your email address" and "Reset your password" mails, the closing "Regards," that the framework's email view prints, the "If you're having trouble clicking the button" note under a button, and the footer's "All rights reserved." are written in English and looked up by their English text. A language translates them in `lang/<code>.json` (`{"All rights reserved.": "Tous droits réservés."}`), which `lang:check` does not read (it compares the `.php` files only), so nothing fails when a language leaves them out: the sentences are then English. Laravel's translations for many languages are in the `laravel-lang/lang` package.
- *The names of a digest's areas* ("Forum updates", "Blog activity") come from `config/notification-preferences.php`, like the labels on the Notifications settings page, and are English.
- *Amounts* are written as a decimal and the currency's code (`12.50 USD`), the same in every language. *Dates* are written by `DateFormatter` in the recipient's own `locale` and time zone, as the rest of the site writes them, so the month in a French member's email is French as soon as Carbon has the language.
- *The Discord text.* The staff mirror and the Discord companion's messages are not emails and stay in English.

## Adding a language

Copy `lang/en` to `lang/<code>`, translate the values, add the code to `APP_SUPPORTED_LOCALES`, and run `php artisan lang:check` until it passes. The whole guide, including what the site does for a visitor and for a new member, and the things a language does not change, is [adding-a-language.md](adding-a-language.md).

## What is translated today

The shared frame of the site is converted to keys:

- The header in full: the navigation and buttons, the search, the account menu, the cart sheet, the notification bell and its panel, the menu on a phone, the skip link, the footer and the theme menu (`lang/en/ui.php`). A count is a plural (`ui.notifications.unread`: "1 unread notification", "3 unread notifications").
- The frame of the settings pages: the title, the description and the 13 entries of the navigation, in both the side list and the tabs of a phone (`lang/en/settings.php`, sent to the settings routes only).
- The seven sign-in and password pages (log in, register, forgot password, reset password, confirm password, verify email, two-factor challenge) with their layout (`lang/en/auth.php`).
- The error pages, the standalone one and the `Error` page (`lang/en/errors.php`, [error-pages.md](error-pages.md)).
- What a member is told when a form or an action is refused ([Form messages](#form-messages)): Laravel's own messages and 71 sentences of the app's own.
- The 21 notification emails, and the notices and browser alerts made from them, in `lang/en/mail.php`, written in the recipient's language ([Emails](#emails)).

Still literal English in 1.0:

- The body of each settings page (its labels, buttons and help text), the command palette (`Ctrl K`), and the "Close" that a dialog or a sheet gives a screen reader (`components/ui`).
- The notices a page flashes after an action ("Saved."), and the explanation given to `abort()` for a 403.
- The admin area, the messages of the API, and the messages that tell whoever runs the site to change a setting.
- The `<title>` of an error page and the other sentences that Laravel writes in English and looks up by their English text (`lang/<code>.json`, as in [Emails](#emails)), which `lang:check` does not read.
- Prices in the cart sheet, which are written with the `en-US` convention (`$1,234.50`) whatever the language.

Converting these is tracked in [docs/ROADMAP-v1.0.0.md](ROADMAP-v1.0.0.md) (section 8B): new screens written for 1.0 use keys from the start, and bulk extraction of the older pages follows in 1.1.

Conventions for new code: use keys, never concatenate translated fragments (a sentence that ends in a link is one string for the link, as "Back to log in" is, not a sentence and a link side by side), and prefer logical CSS utilities (`ms-`, `me-`, `ps-`, `pe-`) so right-to-left layouts stay possible. A key cannot have the same name as a string beside it: `auth.password` is a message, so the word "Password" is `auth.common.password`.
